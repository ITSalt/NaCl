## Подготовка воспроизводимых прогонов

1. Проверить фактическое соединение, project scope, текущие claim-lock и writers; сохранить baseline кода, спецификации, графа и локального .tl состояния. Секреты и пользовательские материалы не включать в публичные отчёты.
2. Проверить способ экспорта и восстановления именно используемого графа до первой мутации. Выбрать ограниченный набор тестовых сущностей с experiment/run ID; если сценарий требует изменения существующих узлов, сохранить их исходное состояние и связи. Полный reset общего графа не делать при работающих чужих сессиях.
3. Кодовые варианты запускать в отдельных экспериментальных worktree от одного commit. Graph-мутирующие прогоны выполнять последовательно под project claim-lock; read-only анализ может идти параллельно. Если параллельное сравнение действительно нужно, использовать копию графа с отдельной identity.
4. Перед каждой парой/повтором восстанавливать одинаковое стартовое состояние и проверять его семантический fingerprint. Общая история предыдущего варианта не должна подсказывать решение следующему. Время snapshot/reset учитывать отдельно от времени разработки и от cold setup методологии.
5. После серии убрать только собственные экспериментальные изменения/locks либо вернуть baseline при подтверждённом отсутствии других writers. Сохранить сырые журналы и отчёт сверки; ошибку восстановления фиксировать как результат, а не скрывать.

## Корпус и сравнение

WP-01 выбирает конкретные задачи из кода, .tl и графа. Для истории доступны .tl/fix-plans, conductor-state archives, gap-closure и QA reports; это кандидаты на corpus, а не уже проверенные кейсы.

Шесть классов сохраняются: малая фича; BE+UI изменение; багфикс; интеграционный контракт; изменение требований; восстановление после прерывания/расхождения. Для каждого зафиксировать IDs, стартовую версию, одинаковый пользовательский brief и независимые acceptance criteria до запуска. Известные агенту решения исторических кейсов исключать из входа или отмечать contamination.

A: действующий NaCl с графом и правилами проекта. B: эквивалентная Markdown-спецификация + Harness. Эксперимент B намеренно не вызывает обязательные NaCl workflow из CLAUDE.md; это ограниченное исследовательское исключение по цели сравнения и D-3, а не изменение постоянных инструкций проекта. Остальные требования продукта, безопасности и тестов одинаковы. Экспортировать в B те же исходные требования, чтобы разница полноты входа не стала преимуществом A. Стоимость преобразования графа в Markdown показывать отдельно.

C: облегчённая методика, если достаточно экспериментальных инструкций без правки скиллов. Сначала один парный pilot для проверки процедуры, затем повторы по общему протоколу; разрешение на использование проекта уже дано. Ресурсный план долгих/платных серий остаётся отдельным расчётом, не повторным запросом доступа к полигону.

Локальные команды-кандидаты из package.json: pnpm lint, pnpm typecheck, pnpm test:be, pnpm test:fe. Перед запуском проверить их определения и зависимости; Node >=24 <25, pnpm >=10.33.0 по package.json. test:be:db требует отдельно подготовленной тестовой прикладной БД; разрешение на граф не означает использование production PostgreSQL. Для внешних AI/платёжных интеграций по умолчанию записанные fixtures/моки, чтобы цена и нестабильность провайдера не смешивались с методологией. Реальные интеграционные вызовы — отдельная явно описанная часть сценария.

## Выход

WP-01: замороженный corpus и baseline manifest. WP-16: живые A/B результаты с tokens/time/owner effort/rework/quality и восстановлением состояния; невозможность отдельного прогона оформляется конкретным ограничением. Отсутствие согласованного тестового проекта больше не является причиной заменить live-исследование только static/replay. Стыковые WP используют те же кейсы; их аналитические выводы сверяются с замерами.
