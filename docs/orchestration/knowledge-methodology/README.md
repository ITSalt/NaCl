# Актуализация знаний и упрощение методологии

Программа `knowledge-methodology` по концепции единого оркестратора (pepper-orchestrator).
Создана 2026-11-02. Тег в сообщениях и заголовках PR: `[KNOWLEDGE]`.

## Где что лежит

| Путь | Что |
|------|-----|
| `status.md` | единственный источник состояния: волны, пакеты работ, очередь владельца, журнал |
| `PLAN.md` | цели, объём, волны, гейты, риски |
| `decisions.md` | решения D-n, допущения A-n, вопросы для исследования Q-n (только дописывается) |
| `work-packages/` | один файл на пакет работ, `_TEMPLATE.md` — шаблон новых |
| `bugs/` | один файл на дефект, найденный по ходу |
| `reports/` | отчёты сверок, живых проверок, гейтов (создаётся по мере надобности) |
| `release/` | листы выкатки, runbook, rollback (создаётся по мере надобности) |
| `orchestration/protocol.md` | протокол сессий и сообщений этой программы |
| `orch.yaml` | модули, сессии, окружения, защитные правила |

## Правила в одном абзаце

Пишет сюда только сессия оркестратора (`knowledge-methodology-coord`). Сессии модулей пишут код в
своих репозиториях и сдают работу через PR. По решению D-1 оркестратор сам выполняет push, merge и публикацию обновлений после проверок.
Merge и выпуск проводятся через `orch.py deliver` / `orch.py release` с проверками и журналом.
Изменения БД, прав и инфраструктуры требуют отдельного разрешения владельца.

Сессии работают локально в Codex; основной checkout NaCl остаётся на своей ветке.
Локальные launch descriptors не коммитятся: на другой машине их создаёт `orch.py settings all`.
Следующий этап — `plan`: определить изменения и проверяемые критерии завершения.


Если наблюдение процесса запрещено или PID скрыт, сохраняй назначения, outbox, слоты и блокировки до восстановления владельцем. Не считай это остановкой процесса, не ослабляй sandbox/approvals, не открывай полный App Server RPC и не устанавливай непроверенный MCP-мост.
