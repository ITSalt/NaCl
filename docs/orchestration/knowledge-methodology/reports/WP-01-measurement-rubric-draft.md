# WP-01: черновик рубрики сравнения

Статус: для последующей проверки, не замороженный протокол и не результат измерений. Основание: `spec/research-protocol.md` и `spec/family-cinema-testbed.md`.

## Единица и фиксация до старта

Один запуск = один вариант A/B на одном кейсе, одной исходной версии и одинаковом brief. До запуска записать ID кейса и повтора, hash стартового кода, версию модели и клиента, права и набор инструментов, состояние кэша, тестовый контур, fingerprint графа и локального состояния либо конкретную причину отсутствия. Вариант A использует зафиксированный NaCl; B получает эквивалентные требования в Markdown с тем же Harness, кодовым контекстом и критериями приёмки. Вход B и стоимость переноса требований фиксируются отдельно. Нельзя скрывать различия окружений под эффектом методологии.

Исторические FR и fix plans могут раскрывать решение. Для обоих вариантов готовится одинаковый минимальный brief; в agent context не включаются поздние решения, тесты, git refs и история с готовым решением. Изолированность и исполнимость нужно проверить перед пилотом; не утверждать, что она обеспечена одной формулировкой prompt. Раздельные временные копии должны сохранять только согласованный baseline. Порядок и seed фиксируются до выбранного запуска. D-4 разрешает одну пару плюс review. Интерпретация одной пары как ограниченной feasibility-проверки предложена координатором, но не является утверждённой поправкой к протоколу: минимум три повтора на сценарий для exploratory pilot сохраняется и не может быть объявлен выполненным одной парой. Для серии нужны отдельные ресурсы; порядок заранее чередуется либо рандомизируется.

## Учёт

| Показатель | Начало / конец или определение | Отсутствующие данные |
|---|---|---|
| Wall time | от выдачи одинакового brief до независимого решения о приёмке; отдельно setup и reset | unknown, не заменять суммой параллельного agent-time |
| Активное время / ожидание | интервалы исполнения и отдельно очередь, owner/permission, сервисы | фиксировать таймстемпы и причину |
| Время владельца | фактические интервалы ручной работы и решений | unknown при отсутствии хронометража |
| Токены / стоимость | input, output, cache отдельно; стоимость только при известном тарифе и модели | unknown и ссылка на источник тарифа |
| Накладные расходы | чтения/записи состояния, вызовы инструментов/агентов, подтверждения, compaction и recovery | считать события по журналам, отдельно от полезной инженерной работы |
| Качество | независимые проверки требований, severity дефектов, missed requirements, false PASS, статус каждой проверки | NOT_RUN и BLOCKED сохраняются, не смешиваются с PASS |
| Надёжность | завершение, возвраты/rework, ложные блокировки, воспроизводимость после прерывания | failure и timeout остаются в знаменателе |

Сырой журнал с отметками времени и итог каждого запуска хранится независимо от отчёта. Неуспешные и прерванные начатые запуски не удаляются из знаменателя; не начатые из-за preflight показываются отдельно. Mandatory NOT_RUN/BLOCKED/UNRESOLVED означает неприёмку без автоматического product FAIL; отдельный FAILED сохраняется рядом. Правило разметки инженерной работы и обслуживания методологии фиксируется до измерений; события классифицируются по этому правилу до сравнения результатов; спорные события остаются с причиной и отдельной категорией.

## Приёмка и сравнение

До запуска для каждого кейса составить таблицу требования → независимый критерий → команда/fixture → ожидаемое наблюдение → severity при нарушении. Независимые проверки не должны требовать конкретной внутренней реализации; в частности, найденный FR-029 тест, использующий внутренний `refreshAllQuotaInstances`, нельзя принять как нейтральный без переработки. Выполнение собственных тестов агента не заменяет независимую приёмку. По возможности reviewer не знает вариант; условия ослепления и фактические исключения записываются.

Сравнивать абсолютные результаты и разброс отдельно по кейсам, cold setup и steady state; пропущенные значения и незавершённые прогоны показывать явно. Порог протокола для перспективного кандидата — медианное сокращение времени не менее 25% при отсутствии новых critical/high дефектов, false PASS и пропущенных обязательных требований. Это порог отбора, а не доказанное свойство или норматив продукта. Три повтора дают только предварительную оценку; одна пара не доказывает медианную экономию 25%. Если приёмка не достигнута, время до принятого результата отсутствует, отдельно показывается время до остановки.

## Необходимые проверки перед запуском

1. Установить воспроизводимый кодовый и графовый baseline, scope, отсутствие конфликтующих writers, безопасный reset и fingerprint. Текущий read-only graph initialize 2026-11-02 завершился timeout; содержимое графа неизвестно.
2. Для каждого исторического commit определить собственный Node/package manager и тестовые команды. FR-014 использует npm и отдельные lockfiles; поздние кандидаты используют pnpm: текущие команды нельзя автоматически переносить на старые снимки.
3. Проверить независимые fixtures, ограничения доступа к истории и отсутствие реальных платёжных/AI вызовов. Определить budget/timeouts для оплачиваемых или длительных запусков.
4. Зафиксировать варианты и acceptance criteria до эксперимента; одна пара D-4 не заменяет серию и до проверки остатка/остановки не запускается. Для анализа предложено отдельно показывать wall time как объединение перекрывающихся интервалов и суммарные agent-minutes, включая setup/reset/review. D-4 не уточняет способ учёта 195 минут и начало подготовки; остаток и точная граница учёта не подтверждены. Cached input не прибавлять повторно к total input, если он уже включён провайдером. При отсутствии hard cap явно назвать доступный контроль soft limit и не утверждать гарантию. A/B пока не запускался.
