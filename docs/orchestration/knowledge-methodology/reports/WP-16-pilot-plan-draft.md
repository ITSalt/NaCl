# WP-16: предложение одного парного pilot

Это подготовленный ресурсный план, эксперимент не запущен. Владелец согласовал лимиты одного парного пилота и review (D-4); до подтверждения остальных гейтов запускать пилот нельзя. D-3 уже разрешает Family Cinema и его граф, повторного разрешения полигона не требуется.

Кандидат FR-014: commit `8d449ab652568d6f1cd69d9c2b9bdae829a6bb79`, tree `ba97fb7ee0b2ccbded3096f75e2d2a64ce4ba3e2`. Две свежие сессии A/B последовательно, одинаковые snapshot/brief/AC, независимый закрытый black-box harness. До запуска зафиксировать порядок и seed, изолированные или одинаково подготовленные caches и состояние reset; отдельно учесть billed input/cache write/cache read без двойного счёта. Одна пара не отделяет эффект порядка от варианта; обратный порядок является дополнительным прогоном вне утверждённой одной пары. Один парный запуск проверяет процедуру, не размер эффекта; exploratory comparison требует минимум трёх повторов по протоколу. На историческом baseline есть frontend npm lock, Vitest/RTL; в отдельной копии проверены установка с отключёнными lifecycle scripts и один узкий unit test. Полная сборка, полный harness, browser/touch и воспроизводимость обеих arm не проверены.

Предложенные лимиты: каждая arm до 60 минут и 500k input + 50k output; независимый review до 30 минут и 200k input + 20k output; setup/reset до 45 минут. Итого до 195 минут и 1.2M input + 120k output, cache read/write учитывать отдельно по фактическому тарифу. Суммарный лимит согласован владельцем D-4; прежнее распределение исчерпывает весь лимит и не оставляет резерва на координатора/подготовку. Оно не является доступным остатком: время и токены уже выполненной агентной подготовки нужно включить в общий расход и уменьшить лимиты arm/review; точные usage и механизм hard stop ещё не подтверждены. Пока общий остаток нельзя доказать, A/B не начинать. Стоимость неизвестна без модели, тарифа и правил cache. Проверить техническую возможность остановки; при отсутствии hard cap явно сообщить soft limit и обеспечить ручную остановку, не утверждать техническое ограничение расходов.

До запуска:

1. Независимый автор получает функциональный brief без post-change решения; evaluator фиксирует hashes brief, fixture и harness. На исходном снимке — ожидаемый RED; контрольная изолированная реализация с сохранённым diff — GREEN. Невалидный harness = invalid/BLOCKED, не провал arm. Запретить обоим исполнителям доступ к post-change Git refs и скрытым тестам технически. Если изоляция не доказана, результат может быть только явно неослеплённым/contamination-unknown исследовательским прогоном, не blind acceptance; доказанная утечка делает пару invalid для blind-схемы. Отсутствие refs в extracted snapshot не запрещает чтение соседнего checkout при текущих правах.
2. Проверить фактическое подключение graph, scope/schema/writers/locks и безопасный snapshot/restore. Кандидат — отдельный sanitized disposable graph с проверенным восстановлением; альтернативный scoped test set с before-image требует доказанного отсутствия конфликтующих writers. Полный import общего графа не использовать.
3. Сверить идентичность требований graph A и Markdown B, code↔graph baseline. Нынешний граф нельзя автоматически считать baseline для исторического `8d449ab`: нужны подтверждённый исторический snapshot либо семантическое восстановление из тех же предварительных материалов с учётом потерь и стоимости миграции; зафиксировать semantic fingerprint scope/schema/IDs/properties/relations и соседней границы, повторить после восстановления. Graph handshake и TCP connect ранее истекли; состояние неизвестно.
4. Зафиксировать фактическую модель, версию клиента/Harness, permissions, тесты и версии окружения, обеспечить отсутствие реальных provider/платёжных вызовов; сохранить raw traces, результаты всех arm, токены/cache, wall и время владельца, reset отдельно. При неготовности baseline, независимого harness или изоляции остановить как BLOCKED/invalid.
